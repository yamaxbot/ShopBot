# ShopBot — группы игровых аккаунтов на Playerok и FunPay

## Группы и статистика

Каждая группа продаёт одну игру и один тип аккаунтов. У неё отдельный склад,
история, объявления, резерв и процесс обслуживания. Все пользователи также
изолированы друг от друга. Подключения к площадкам общие для групп одного продавца.

```text
/group_new CPM 2 — прокачанные
/items
/fp_items
/add login@example.test:password
/check
/run
```

Создание группы сразу выбирает её. `/groups` показывает номера и состояние;
`/group 1` выбирает существующую группу, `/group_rename Новое название`
переименовывает её. Все новые аккаунты, лоты и команды `/run`, `/stop`, `/check`,
`/stats` относятся к выбранной группе. Остальные запущенные группы продолжают работу.
`/stop_all` останавливает все группы пользователя. Изменение авторизации площадки
останавливает все его группы; запустите нужные заново. Один аккаунт или лот нельзя
привязать к двум группам; очистка списка лотов не снимает защитную привязку.
Перенос уже зарезервированного или проданного товара между группами не выполняется.

- `/stats` или `/status`: склад, ошибки и деньги выбранной группы за всё время.
- `/allstats`: суммарный отчёт всех ваших групп за всё время.
- `/daily`: текущий день выбранной группы, кнопки предыдущего/следующего дня.
- `/daily 2026-10-17`: конкретный день, границы суток по МСК.
- `/daily all` или `/daily all 2026-10-17`: дневной отчёт по всем вашим группам.
- `/fees`: ставки выбранной группы; `/fees playerok 0 6` и `/fees funpay 0 3`
  задают комиссию продажи и комиссию вывода в процентах.
- `/bump_status`: таймер, последнее состояние и ошибки поднятия каждого Playerok-лота.
- `/commands`: полный список команд; `/help`: порядок работы, резервы, карантин,
  неоднозначные изменения лотов и ограничения статистики.

Комиссия вывода по умолчанию: **Playerok 6%, FunPay 3%**; дополнительная комиссия
продажи для расчёта по умолчанию 0%. Ставки фиксируются при записи продажи;
изменение ставки не пересчитывает ранее заполненные значения. Вывод считается
от суммы после комиссии продажи. Все вычисления ведутся в копейках с округлением.
Отчёт показывает количество заказов и аккаунтов, сумму продаж, ожидающие и
подтверждённые сделки, возвраты, оценку после комиссий, учтённые расходы на
публикации/поднятия и средний заказ. Это оценка поступлений, не баланс кошелька
и не чистая прибыль: закупочная стоимость аккаунтов не учитывается.

День определяется датой покупки из API, а при её отсутствии — датой обнаружения
(это отдельно отмечено в отчёте). Возврат корректирует день исходной покупки.
Полный возврат исключается из выручки; частичный возврат и суммы в другой валюте
не складываются с известными суммами RUB. Повторное чтение заказа не удваивает деньги.
Старая история без сохранённой цены остаётся с неизвестной суммой; текущая цена
объявления не используется для восстановления старой выручки. Бот не импортирует
произвольные продажи всего магазина, не связанные с учтённым товаром.
Неизвестные списания и расходы до установки этой версии не включаются в известные расходы.

### Обновление существующей установки

Остановите контейнер и сохраните `.env` и всю `data/` перед обновлением:

```bash
cd ~/playeroc_bot2
docker compose stop telegram-bot
tar -czf ../shopbot-backup-$(date +%Y%m%d-%H%M%S).tar.gz .env data
git pull --ff-only origin main
docker compose up -d --build telegram-bot
```

Миграция автоматически создаёт группу **«Основная»** из прежних настроек.
Её база остаётся по прежнему пути `users/<Telegram ID>/inventory.sqlite3`;
новые группы используют `users/<Telegram ID>/groups/<ID>/inventory.sqlite3`.
Перед миграцией реестра создаётся `profiles.before-groups.sqlite3`.
Существующие аккаунты и история не удаляются. Сохраняйте весь `data/telegram`,
включая `secret.key` и `ownership.sqlite3` каждого пользователя.

### Исправления поднятия Playerok

Ошибка чтения продаж больше не пропускает проверку поднятия. Если перед оплатой
статус или время изменились и платный запрос пропущен, двухчасовой таймер
не сбрасывается. Пустой/чужой ответ API не считается успешным поднятием.
Ожидание и ошибки доступны в `/bump_status`, ошибки также уведомляют в Telegram.
Сохраняются отдельные таймеры, лимит цены, защита от частых повторов при неизвестном
результате и запрет поднятий с 00:00 до 12:00 МСК. Реальный результат зависит от
ответов Playerok; обновление не обходит модерацию или ограничения площадки.

## Telegram для нескольких пользователей

Режим по умолчанию — Telegram-бот на aiogram. Каждый пользователь в личном
чате подключает свои Playerok и/или FunPay, задаёт до трёх премиум-лотов
Playerok и до восьми лотов FunPay. Настройки и склад аккаунтов разделены по
Telegram ID. Один профиль каждой площадки нельзя привязать к двум пользователям.

Для запуска в `.env` достаточно настроек Telegram:

```dotenv
TELEGRAM_BOT_TOKEN=токен_от_BotFather
TELEGRAM_DATA_DIR=data/telegram
TELEGRAM_MAX_WORKERS=20
TELEGRAM_ALLOWED_USER_IDS=
```

Пустой `TELEGRAM_ALLOWED_USER_IDS` разрешает регистрацию всем пользователям
в личных сообщениях. Для закрытого бота укажите числовые ID через запятую.
Групповые чаты Telegram не поддерживаются. `TELEGRAM_MAX_WORKERS` ограничивает
общее число одновременно работающих товарных групп всех продавцов.

Если прямое подключение к Telegram недоступно, задайте необязательный
`TELEGRAM_PROXY=http://адрес:порт` в окружении или `.env`. Для локального
запуска в Windows можно использовать работающий прокси на `127.0.0.1`.
На сервере или внутри Docker укажите адрес, доступный именно из контейнера.

Запуск на сервере:

```bash
docker compose down --remove-orphans
docker compose up -d --build telegram-bot
docker compose logs -f telegram-bot
```

Каждый пользователь открывает бота и выполняет:

1. `/start` — инструкция.
2. `/connect` — ввод cookie token своего профиля Playerok. User-Agent бот подставит сам.
3. `/items` — ссылки на свои активные премиум-объявления, по одной на строку.
4. Отправка аккаунтов, включая точные данные, уже указанные в каждом лоте.
5. `/check` — проверка настройки; `/run` — запуск автовыдачи.

`/start` показывает короткую инструкцию. `/commands` показывает полный список,
а `/help` объясняет работу бота; справку можно открыть во время настройки и затем
продолжить ввод. `/stats` и `/status` показывают только ваши продажи, остатки,
резервы и ошибки обеих площадок. Reply-клавиатуры нет; команды доступны через
меню команд Telegram. Доступны также `/stop`, `/settings`, `/limit` и `/cancel`.
`/bump on` и `/bump off` включают или выключают платные плановые поднятия.
При изменении настроек продажи останавливаются; для продолжения выполните
`/run`. Лимит стоимости по умолчанию — 50 ₽ за публикацию или поднятие.
Если Playerok-лот добавлен по ошибке, `/items clear` убирает его из настроек
бота, не меняя объявление на сайте. Затем можно подключить FunPay через
`/fp_connect` и `/fp_items` и снова выполнить `/run`.

Если `/check` или `/run` сообщает о таймауте, смотрите этапы проверки
в `data/telegram/users/ВАШ_TELEGRAM_ID/probe.log`. Журнал содержит названия
этапов и типы ошибок без cookie, паролей и ответов API. Последний этап
показывает, где остановилась проверка; это ещё не объясняет причину задержки.
Проверка обеих площадок начинается с FunPay. `/fp_check` проверяет только FunPay.
Работающий обработчик пишет в `marketplaces.log` и `console.log` в том же каталоге.
Убедитесь через `/settings`, что автовыдача работает: `/check` сам её не запускает.

Аккаунты принимаются обычным сообщением, командой `/add` или файлом `.txt`
в UTF-8 размером до 512 КБ. Форматы можно смешивать:

```text
first@example.com:first-password
Логин second@example.com Пароль second-password
login=third@example.com password=third-password
fourth@example.com|fourth-password
Логин: fifth@example.com
Пароль: fifth-password
```

Весь пакет проверяется до импорта. Дубликаты пропускаются; проданные записи
не становятся новыми. После успешного импорта сообщение с паролями удаляется
из чата, если Telegram разрешает удаление. Очередь пополняется без остановки
автовыдачи. После каждых 10 завершённых продаж пользователь получает свой
остаток аккаунтов. Для FunPay учитывается количество выданных аккаунтов,
подтверждённых содержимым заказов, включая несколько товаров в одном заказе.

У каждой группы отдельный процесс PlayerokAPI: библиотека использует
singleton аккаунта, поэтому разные авторизации нельзя запускать в одном
интерпретаторе. После перезапуска Telegram-хоста запущенные профили возобновятся.
После ошибки отдельного процесса пользователю приходит уведомление; очередь
сохраняется. Два хоста с одной папкой данных одновременно не запускаются.

Данные находятся в `data/telegram`: зашифрованные настройки в
`profiles.sqlite3`, ключ в `secret.key`, личные очереди и журналы в
`users/<Telegram ID>/`. Для резервной копии сохраняйте весь каталог, включая
ключ. Товарные логины и пароли хранятся в личной SQLite-базе; другим
пользователям бот их не показывает. Пароли и cookies в ответы не выводятся.

### Подключение FunPay

1. Создайте вручную от 1 до 8 предложений для одинаковых аккаунтов одной группы.
   Цены и описания могут различаться; категория и параметры товара должны совпадать.
   Включите встроенную автовыдачу. Запас в лоте может быть пустым.
2. В личном чате выполните `/fp_connect`. Отправьте значение cookie `golden_key`
   (F12 → Application → Cookies → funpay.com). User-Agent бот подставит сам.
   Авторизация хранится зашифрованно.
3. `/fp_items` — отправьте до 8 ссылок или числовых ID, по одному на строку:

   ```text
   https://funpay.com/lots/offer?id=123456
   https://funpay.com/lots/offer?id=123457
   ```

4. Отправьте боту аккаунты сообщением или файлом `.txt`. Уже находящиеся в
   FunPay-лотах данные бот учтёт при запуске; их необязательно загружать повторно.
   Данные текущих Playerok-лотов по-прежнему нужно добавить самостоятельно.
5. `/fp_check` — проверка FunPay без публикаций и изменения товаров.
   `/check` проверяет все настроенные площадки; `/run` запускает их вместе.
   Можно использовать только FunPay и не подключать Playerok.
6. `/stats` показывает склад, резерв Playerok, запас каждого FunPay-лота,
   подтверждённые выдачи и несверенные изменения. `/stop` останавливает
   управление обеими площадками. **Уже загруженные товары FunPay продолжат
   выдаваться самой площадкой**, пока вы не отключите лоты на сайте.

### Распределение и пополнение

- У каждого Telegram-пользователя свой склад. Один аккаунт одновременно
  закрепляется только за одной площадкой и одним лотом.
- При настроенном Playerok **5 запасных аккаунтов** остаются в его резерве,
  сверх аккаунтов в 1–3 активных объявлениях. После продажи резерв пополняется
  со свободного склада. При нехватке товара он будет меньше пяти.
- FunPay проверяется в каждом цикле (пауза между циклами 30 секунд плюс время
  запросов). Каждый лот пополняется **до 5 аккаунтов**, когда на свободном складе
  есть товар. При нехватке добавляется доступное количество; остаток пополнится
  после следующей загрузки аккаунтов. Если свободных аккаунтов нет, лот остаётся
  как есть. Резерв Playerok и товар других FunPay-лотов не используются.
- После пополнения бот поднимает активные FunPay-лоты с товаром при первой
  доступной проверке. Время следующей попытки берётся из ответа FunPay и
  сохраняется в личной базе продавца, поэтому перезапуск не сбрасывает ожидание.
  Если ответ о поднятии потерян, повтор откладывается на 10 минут. Если FunPay
  не прислал время ожидания, бот проверит снова через минуту. Поднятие действует
  на **все ваши предложения в той же подкатегории**, включая не добавленные
  в бота: FunPay не принимает ID отдельных лотов в этом запросе. Ограничение
  ночных поднятий Playerok к FunPay не относится.
- Для 8 полностью заполненных FunPay-лотов, трёх активных Playerok-лотов и
  его резерва нужно **48 разных аккаунтов: 40 + 3 + 5**.
- При исчерпании запаса лот FunPay не активируется без товара. Добавленные
  через Telegram аккаунты работающий бот загрузит автоматически.
- Изменение настроек останавливает ваш процесс. После `/fp_items` или
  `/fp_connect` выполните `/run`. Другие пользователи продолжают работу.
  Убранные из настроек лоты перестают обслуживаться, но их товары остаются
  зарезервированы и не возвращаются на склад автоматически.

Перед обновлением лот временно деактивируется. Бот читает новую форму,
сохраняет товары и проверяет результат, затем активирует лот. Цены, описания,
фотографии и остальные поля
берутся из свежей формы и сохраняются. Во встроенную выдачу каждый аккаунт
записывается одной строкой: `Логин: адрес Пароль: значение`. Уже загруженные
аккаунты в управляемых лотах бот переводит на этот формат при следующей сверке.

Протокол адаптера основан на исходниках
[FunPayAPI в FunPayCardinal](https://github.com/sidor0912/FunPayCardinal/blob/main/FunPayAPI/account.py)
и [funpay-mcp](https://github.com/DKeken/funpay-mcp).
Используются `golden_key`, формы `offerEdit`/`offerSave`, токены свежей формы
`csrf_token`/`form_created_at` и API заказов. Это неофициальный интерфейс;
его совместимость с вашим аккаунтом проверяет `/fp_check`. Поднятие использует
`lots/raise` для подкатегории, а не отдельного предложения. Проверки проекта
используют имитацию площадки; реальные пополнение и поднятие FunPay пока не запускались.

### Неизвестный результат сохранения FunPay

Журнал изменений и резервы сохраняются в личной SQLite-базе. Если ответ
потерялся, бот сверяет фактическое содержимое лота, не отправляя тот же запрос
ещё раз. Если результат подтверждён, работа продолжится автоматически после
перезапуска. Если аккаунт успел выдаться, подтверждение ищется в заказе.
Явно отклонённую сервером форму можно повторить с новыми токенами.

Если однозначно подтвердить результат нельзя, пользователь получает уведомление,
а затронутые лоты блокируются для дальнейших изменений. `/fp_errors` показывает
номера операций и лотов; `/stats` — количество товара в карантине.
Исчезновение из лота само по себе не считается продажей: товар мог быть удалён
вручную. Он не возвращается на склад и не выдаётся повторно. Выданный товар
не возвращается в очередь и при возврате денег покупателю.

Для ручной диагностики выполните `/stop`, сохраните резервную копию
`data/telegram`, сопоставьте товары и историю заказов на FunPay с журналом
личной базы `funpay_edits`. В журнале хранятся отпечатки аккаунтов, а не пароли;
в `accounts` — исходные данные. Не удаляйте базу или резервы для устранения
ошибки и не загружайте повторно товар с неизвестным результатом. Если содержимое
вновь совпадёт с подтверждаемым результатом операции, `/run` продолжит сверку.
Пока бот обслуживает лоты, редактируйте их запас через бот, чтобы внешние
правки не вмешивались в переносы. Проверка удаления и журнал сокращают риск
дублирования, но серверная обработка параллельных покупок вне контроля бота;
абсолютную гарантию атомарности неофициальный интерфейс не предоставляет.

### Обновление уже развёрнутого Telegram-бота

Сохраните серверные `.env` и каталог `data`; замените только код и файлы сборки.
На сервере:

```bash
cd ~/playeroc_bot2
docker compose down --remove-orphans
docker compose up -d --build telegram-bot
docker compose logs --tail=100 telegram-bot
```

SQLite-схемы обновляются автоматически без удаления очереди и истории.
Повторно выполнять `migrate-user` для уже перенесённого Telegram-профиля не нужно.
Dockerfile устанавливает зависимости обеих площадок; отдельный контейнер FunPay
не требуется. Токены FunPay не добавляйте в общий `.env`: каждый вводит свои в чате.

### Перенос существующего магазина

Если у вас уже есть рабочая база и продажи, сохраните серверные `.env` и
`data`. Загрузите новый код, затем остановите контейнеры и перенесите базу в
профиль своего числового Telegram ID:

```bash
docker compose down --remove-orphans
docker compose build telegram-bot
docker compose run --rm telegram-bot migrate-user --user-id ВАШ_TELEGRAM_ID
docker compose up -d telegram-bot
```

Команда берёт прежние Playerok-настройки из серверного `.env`, проверяет
авторизацию и копирует `data/playerok_bot.sqlite3` через SQLite backup.
Исходная база сохраняется. Если в личной базе уже есть аккаунты, перенос
отменяется. После переноса откройте `/stats`, `/check`, затем `/run`.
Не запускайте прежний одиночный бот для того же Playerok параллельно с
Telegram-профилем.

## Одиночный режим с accaunts.txt

Бот обслуживает от одного до трёх премиум-лотов. После оплаты он учитывает продажу,
подставляет следующий аккаунт из очереди, добавляет комментарий
`приятного пользования` и снова публикует тот же лот с премиум-статусом.
У каждого лота свой аккаунт; свободные аккаунты берутся из общей очереди
в порядке строк файла.

Аккаунты добавляются вручную в `accaunts.txt`. Бот перечитывает файл каждые
15 секунд, импортирует новые строки в SQLite и пропускает уже импортированные
аккаунты. Когда запас закончится, лот останется снятым с продажи. После
добавления новых строк работающий бот автоматически восстановит его.

## Первый запуск

1. Остановите прежнего бота, если он уже работает.
2. Создайте до трёх активных премиум-лотов в разделе Car Parking Multiplayer 2
   → Аккаунты. Новые объявления создаются вручную.
3. В каждом лоте укажите отдельный непроданный аккаунт и комментарий
   `приятного пользования`. Один аккаунт нельзя указывать в нескольких лотах.
4. Отключите «Оставлять в продаже» в каждом лоте.
5. Добавьте точные данные всех выставленных аккаунтов в `accaunts.txt`, затем
   остальные непроданные аккаунты в нужном порядке.
6. Заполните ссылки в `.env` и выполните проверку перед запуском.

Название, описание, изображение и характеристики лота должны соответствовать
всем аккаунтам в очереди. Все лоты должны относиться к Car Parking Multiplayer 2.
Для оформления используются `name.txt`,
`description.txt` и `image.png`.

## Формат accaunts.txt

Один аккаунт на строку. Поддерживаются оба формата, их можно смешивать:

```text
first@example.com:first-password
Логин second@example.com Пароль second-password
```

Файл сохраняйте в UTF-8. Строки, начинающиеся с `#`, игнорируются.
Специальные символы в паролях сохраняются. В формате `логин:пароль` разделение
выполняется по первому двоеточию.

Новые аккаунты дописывайте в конец файла. Бот сам импортирует их при следующей
проверке; перезапуск не нужен. Если редактор записывает файл в момент проверки,
неудачный импорт повторится в следующем цикле. Уже загруженная очередь при
ошибке файла продолжает работать.

Файл может быть пустым. При первом запуске бот ожидает появления в файле
точных данных аккаунтов всех настроенных лотов, затем начинает обрабатывать
продажи. В журнале указаны номера лотов с недостающими аккаунтами. Начальные
аккаунты всех лотов резервируются перед обработкой первой покупки.

## Настройки .env

Если файла ещё нет, скопируйте `.env.example` в `.env`. Заполните:

```dotenv
PLAYEROK_TOKEN=ваш_token_cookie
PLAYEROK_USER_AGENT="полный User-Agent браузера"
PLAYEROK_ITEM=https://playerok.com/products/ссылка-на-лот
PLAYEROK_ITEM_2=https://playerok.com/products/ссылка-на-второй-лот
PLAYEROK_ITEM_3=https://playerok.com/products/ссылка-на-третий-лот
```

Для одного лота оставьте `PLAYEROK_ITEM_2` и `PLAYEROK_ITEM_3` пустыми. Для
трёх укажите три разные ссылки. Старая настройка `PLAYEROK_ITEM` продолжает
работать. Один контейнер обслуживает все настроенные лоты.

Токен берётся из cookie `token` в браузере, где выполнен вход в Playerok:
F12 → Application → Cookies → https://playerok.com. User-Agent можно увидеть
в заголовке `user-agent` запроса в Network.

Если одного токена недостаточно, укажите полный набор cookie в
`PLAYEROK_COOKIES` в формате `name=value; name2=value2`. Это значение имеет
приоритет над `PLAYEROK_TOKEN`.

Основные настройки:

```dotenv
ACCOUNTS_FILE=accaunts.txt
DATABASE_PATH=data/playerok_bot.sqlite3
LOG_PATH=logs/playerok_bot.log
DELIVERY_COMMENT=приятного пользования
PREMIUM_PRICE_LIMIT_RUB=50
AUTO_CONFIRM_DEAL=true
SEND_COURTESY_MESSAGE=false
RECONCILE_SECONDS=15
```

`PREMIUM_PRICE_LIMIT_RUB` ограничивает стоимость одной публикации каждого лота. При
превышении лимита восстановление ожидает следующей проверки. Для публикации
нужен достаточный баланс Playerok.

`AUTO_CONFIRM_DEAL=true` отмечает оплаченную сделку как отправленную.
`SEND_COURTESY_MESSAGE=true` дополнительно отправляет текст из
`COURTESY_MESSAGE` покупателю в чат.

## Поднятие после двух часов без продаж

У каждого настроенного лота отдельный таймер. Если его не покупали два часа,
бот отправляет запрос повышения премиум-приоритета активного объявления через
PlayerokAPI (`increase_item_priority_status`). После поднятия начинается
новый двухчасовой отсчёт. Данные выдачи при поднятии сохраняются.

```dotenv
AUTO_BUMP_ENABLED=true
AUTO_BUMP_SECONDS=7200
```

Плановые поднятия разрешены с 12:00 до 00:00 по Москве. С 00:00 включительно
до 12:00 они запрещены. Время и часовой пояс сервера на это не влияют. Если
срок истёк ночью, лот будет поднят после 12:00 при ближайшей проверке; за
пропущенные интервалы дополнительные поднятия не выполняются.

Покупка и публикация следующего аккаунта сбрасывают таймер только своего
лота. Ночное ограничение относится к плановым поднятиям: обработка покупок
и восстановление после продажи или пополнения работают круглосуточно.

Поднятие оплачивается с баланса Playerok. Лимит одной операции —
`PREMIUM_PRICE_LIMIT_RUB`. Если цена выше лимита, платный запрос не отправится.
После первого включения функции отсчёт начинается с запуска. Дальше таймеры
хранятся в SQLite и сохраняются при перезапуске.

Перед платным запросом попытка записывается в базу. Если ответ потерялся,
следующая плановая попытка допускается через два часа и в разрешённое время.
Неизвестный результат отражается в `status`; проверьте журнал и платежи
Playerok. На сервере должен работать один экземпляр бота.

Чтобы отключить плановые поднятия, установите `AUTO_BUMP_ENABLED=false` и
пересоздайте контейнер. Логика продаж и восстановления продолжит работать.

Если поля выдачи не определились автоматически, заполните точные подписи:
`LOGIN_FIELD_LABEL`, `PASSWORD_FIELD_LABEL`, `COMMENT_FIELD_LABEL` или
`COMBINED_FIELD_LABEL` для единого поля данных.

## Запуск на сервере через Docker Compose

Нужны Docker и Docker Compose. В каталоге проекта должны находиться
`.env` и `accaunts.txt`.

```bash
mkdir -p data logs
docker compose build
docker compose run --rm playerok-bot check
```

После сообщения «Проверка пройдена» запустите:

```bash
docker compose --profile standalone up -d playerok-bot
```

Статистика и журнал:

```bash
docker compose run --rm playerok-bot status
docker compose logs -f playerok-bot
```

Новые аккаунты добавляйте в серверный `accaunts.txt`. Они подхватятся
автоматически, включая пополнение после полного исчерпания запаса.

Остановка:

```bash
docker compose down
```

При обновлении с версии, в которой был Telegram-сервис, выполните:

```bash
docker compose down --remove-orphans
docker compose --profile standalone up -d --build --remove-orphans playerok-bot
```

База сохраняется в папке `data`, журналы — в `logs`. Секреты и аккаунты
не включаются в Docker-образ. Рабочие файлы подключаются при запуске.

## Локальный запуск на Windows

Установка:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\install.ps1
```

Проверка, запуск и статистика:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\check.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\run.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\status.ps1
```

Проверка не публикует товары и не оплачивает премиум. Она проверяет
авторизацию, принадлежность каждого лота, игру, поля выдачи, разные начальные
аккаунты, настройки и лимит цены. Статистика показывает общий запас,
количество выставленных аккаунтов и продажи по каждому ID лота.
Для остановки нажмите Ctrl+C.

## Сохранение очереди

SQLite хранит выданные аккаунты, ID сделок и этапы восстановления.
При перезапуске бот продолжает незавершённую операцию. Перед повторной
оплатой публикации он проверяет, активен ли уже лот.

Если запаса не хватает для всех лотов, восстановятся те, для которых удалось
зарезервировать аккаунт; остальные ожидают пополнения. Очередь распределяется
в порядке ссылок в `.env`. Ошибка обработки одного лота записывается в журнал
и не останавливает работу остальных. После исправления бот повторит операцию.

При переходе с одного лота на три сохраняйте существующую рабочую SQLite-базу
и первую ссылку. Добавьте две новые ссылки и их аккаунты в файл, затем
выполните проверку и пересоберите контейнер. История предыдущих продаж
сохранится.

Не удаляйте `data/playerok_bot.sqlite3` после начала продаж. При переносе на
другой сервер переносите эту базу вместе с проектом. Добавление новых строк
не сбрасывает историю. Удаление строки из файла не удаляет её из базы.

Аккаунты и пароли хранятся в файле и SQLite. `.env` даёт доступ к профилю
Playerok. Держите эти файлы в своём распоряжении. Одновременно запускайте
один экземпляр Playerok-бота.


## Платный доступ и выгрузка склада

Перед обновлением остановите Telegram-хост и сохраните `.env` и всю папку `data`.
В `.env` обязательно задайте `TELEGRAM_ADMIN_IDS=ваш_числовой_Telegram_ID`
(несколько ID через запятую). Администраторы пользуются ботом без оплаты.
`TELEGRAM_ALLOWED_USER_IDS` — отдельный необязательный список допущенных пользователей,
он не назначает администраторов. Без администраторов счета не выставляются.

Тариф первого запуска: **100 Telegram Stars за 30 дней**, сразу на все группы продавца.
Это предоплаченный доступ с ручным продлением, без автоматических списаний.
После обновления существующим пользователям тоже нужна подписка; их данные не удаляются.
По истечении срока обработчики групп останавливаются (проверка раз в 10 секунд).
Объявления на сайтах и встроенная автовыдача FunPay сами не выключаются.

- `/subscription` — тариф и срок доступа.
- `/subscribe` — условия; `/subscribe agree` — согласие и счёт в Stars.
- `/payments` — последние 30 платежей пользователя.
- `/terms`, `/paysupport`, `/support` — условия и контакты администратора.
- `/admin` — административная справка.
- `/set_price 100 30` — новая цена и срок в днях; второй аргумент можно опустить.
- `/admin_payments TELEGRAM_ID` — последние 30 платежей продавца.
- `/refund НОМЕР` — сумма, получатель и команда подтверждения полного возврата.
- `/refund НОМЕР confirm` — вернуть Stars через Telegram по исходному платежу.

Права администратора проверяются для каждой команды. Изменение тарифа не меняет
уже оплаченный срок или выставленные счета (счёт действует 30 минут).
Оплата учитывается только по `successful_payment`; повторное событие не продлевает
доступ второй раз. При возврате срок этого платежа исключается из расчёта подписки.
При неизвестном результате возврата платёж остаётся `refund_pending`, его срок
временно не даёт доступ; повторите ту же команду для сверки. Не удаляйте базу
`profiles.sqlite3`: в ней находятся счета, платежи и журнал административных действий.
Документация оплаты: https://core.telegram.org/bots/payments-stars .

### Забрать непроданные аккаунты

`/export` — инструкция для **выбранной группы**. Функция доступна без подписки.
Сначала `/stop`, затем вручную снимите лоты этой группы с продажи на Playerok и
FunPay, не удаляя их ссылки из настроек. Завершите сделки и сверку карантина.
Не меняйте лоты и файлы аккаунтов во время выгрузки.

`/export_confirm ID_ГРУППЫ` проверяет принадлежность и неактивность лотов,
очищает автовыдачу неактивных лотов FunPay и присылает `.txt` с логинами и паролями.
Playerok-объявления не удаляются: при недоступном или удалённом лоте бот не может
проверить его состояние и не выдаёт его аккаунт автоматически.

Только после подтверждённой отправки файла Telegram аккаунты удаляются из рабочего
склада, файл импорта группы очищается, ссылки отвязываются. История продаж и отпечатки
выведенных аккаунтов сохраняются для защиты от повторного импорта. Данные в старых
резервных копиях и данные неактивного объявления Playerok не стираются.
Не публикуйте эти объявления вручную с прежними данными после выгрузки.

При сбое группа остаётся остановленной и заблокированной от пополнения.
Повторите `/export_confirm ID_ГРУППЫ`: состояние снятия и отправки восстанавливается.
`/export_cancel` отменяет подготовку, пока файл не подготовлен и нет неизвестного
результата снятия товара. `/export_file` повторно присылает последний файл из Telegram,
не сохраняя его пароли в рабочей базе. Проданные аккаунты и карантин не выгружаются;
если остались неподтверждённые операции, выгрузка блокируется до сверки.


### FunPay возвращает HTTP 429

Это ограничение частоты запросов, а не доказательство неверного golden_key.
Telegram-хост выдерживает общий интервал не менее 3 секунд между запросами всех
групп и проверок FunPay. При 429 запросы приостанавливаются минимум на 2 минуты;
повторные ограничения увеличивают паузу, более длительный `Retry-After` соблюдается.
Пауза хранится в `data/telegram/funpay_rate.sqlite3` и сохраняется при перезапуске.
Не удаляйте этот файл для ускорения запросов. Запущенные группы продолжат работу
после ожидания; если `/run` не прошёл проверку из-за паузы, повторите его после неё.
`/fp_errors` показывает причину и этап ошибки. Если сайты используются другими
программами с того же IP, они тоже могут влиять на лимиты FunPay.
